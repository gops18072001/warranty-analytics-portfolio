# Automotive Warranty Analytics

Warranty and component-quality analysis on a simulated automotive dataset:
227,740 claims against 12.5 million units produced across 30 months, six
suppliers and five plants.

I spent a year and a half as a design engineer at Spark Minda working on
instrument cluster validation, so this is the domain I know. I wanted a project
where I understood what the numbers meant rather than one where I could only
describe the method.

Everything here runs off one dataset. A single domain analysed properly seemed
more useful than four unrelated notebooks.

## About the data

The dataset is **synthetic**. It is generated by
[`generate_data.py`](01_sql_warranty_analytics/generate_data.py) from a fixed
seed (`20260916`), so it rebuilds identically on any machine. It is not real
manufacturer data and no confidential information is involved.

I generated it rather than using a public dataset for one reason: the generator
seeds specific quality problems into the data, so I know the ground truth. That
turns the analysis into something testable — if the queries don't recover the
seeded signals, the queries are wrong. Most public datasets give you no way to
check whether your answer is right.

| Table | Rows | Grain |
|---|---|---|
| `plants` | 5 | one manufacturing site |
| `suppliers` | 6 | one component supplier |
| `components` | 10 | one part type |
| `defect_types` | 10 | one failure mode |
| `production_batches` | 4,584 | one batch produced |
| `warranty_claims` | 227,740 | one field failure |

A star schema with **two fact tables at different grains** — one batch has many
claims. That detail causes most of the ways this data can be analysed wrongly;
see the note on join fan-out below.

Totals: 12.5M units, a 1.82% overall claim rate, and INR 127 crore of warranty
cost between January 2024 and June 2026.

## What the analysis found

**One supplier accounts for 52% of warranty cost on 20% of the volume.** Shreeji
Connectors runs a 4.80% claim rate against a 1.82% fleet average — roughly INR 41
crore more than average performance would have cost.

**It degraded; it was not always bad.** Its rate held near 4.0% through 2024,
then moved to 5.87% in 2025-Q2 and 9.67% in 2025-Q3. A step change like that
points at a datable process or material change, which is a far more actionable
conclusion than "this supplier is poor" — it gives you a window to investigate.

**Older plants run hotter.** Gurugram, commissioned 2012, sits at 2.13% against
Chennai's 1.61% from 2021.

**Failures concentrate.** Six component/defect pairs — largely connector-related
faults on Connector Assembly and Switch Panel — carry over half of total spend.

## Two things worth reading the code for

These were the substance of the work. Both are documented inline in
[`analysis.sql`](01_sql_warranty_analytics/analysis.sql).

### Join fan-out

`production_batches` to `warranty_claims` is one-to-many. Joining them and then
summing `units_produced` multiplies every batch's unit count by its number of
claims. My first version of Q1 reported 767 million units against a true 12.5
million.

Nothing errors. The query runs and returns a confident, wrong number. I only
caught it because the total was implausible against what I knew the generator
had produced. Every query here that needs both a units measure and a claims
measure now aggregates claims to one row per batch first.

### Right-censoring

Parts in this data fail between 20 and 400 days after production, and the data
ends 2026-06-30. Recent batches simply have not had time to fail yet.

The effect is that **every supplier appears to improve sharply in the final
quarter**, and none of them is. A trend chart drawn without accounting for it
shows a quality improvement that does not exist. Comparing periods honestly
means comparing batches that have had a similar amount of time in the field.

## Running it

```bash
cd 01_sql_warranty_analytics
python3 generate_data.py                 # builds warranty.db and csv/
sqlite3 warranty.db < analysis.sql       # runs all eight questions
```

Rebuild the Excel workbook (needs `warranty.db`):

```bash
cd ../04_excel_analysis
pip install openpyxl
python3 build_workbook.py                # writes Warranty_Analysis.xlsx
```

The natural-language query tool:

```bash
cd ../03_genai_nl2sql
pip install -r requirements.txt
export ANTHROPIC_API_KEY=...
python3 nl2sql.py --explain "which supplier costs us the most in warranty?"
```

`warranty.db` and `csv/` are not committed — they are regenerated by the script
and total around 27 MB.

## Techniques

Star-schema modelling, multi-table joins, CTEs, window functions (`RANK`,
`LAG`, running totals, moving averages), conditional aggregation, Pareto
analysis, date bucketing and cohort/maturity reasoning, DAX measures, Excel
formula modelling with `SUMIF` and nested `IF`, and schema-grounded SQL
generation guarded by a read-only connection and a statement allowlist.
